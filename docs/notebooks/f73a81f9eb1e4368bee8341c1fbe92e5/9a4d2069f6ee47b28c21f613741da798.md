# Function Calling

## 1. Function Calling 是什么

Function Calling 是模型和应用程序配合使用工具的机制。程序告诉模型有哪些工具及其参数；模型可以提出使用某个工具的请求；程序找到并执行工具，把执行结果交回模型；模型再根据结果组织回答。

`multiply` 这样的 Python 函数是工具本身。模型提出的某一次“使用 `multiply`，参数为 `a=2、b=3`”是一次工具调用请求。广义的 Function Calling 则指这一整套协作流程。

最重要的职责划分：**模型提出请求，程序执行函数**。模型返回函数名和参数时，函数还没有因此自动执行。

## 2. 为什么需要工具

用户问“杭州现在天气怎么样”时，模型可以理解问题，但要获得实时数据，应用通常需要查询天气服务。模型可以提出查询请求，程序执行天气工具，然后把查到的数据交回模型。模型能使用工具并不意味着工具请求或返回结果一定正确，程序仍要检查调用权限、参数和执行结果。

## 3. 三个角色和一次完整流程

- **模型**：理解问题，结合工具描述决定是否提出调用请求，并生成工具名和参数。
- **应用程序**：作为客户端请求模型，处理返回消息，查找并执行工具，将结果交回模型。
- **工具**：执行具体工作，例如计算、查询天气或访问数据库。

以乘法为例，下面的数据是示意，不是保证每次都会出现的实际模型输出：

```text
用户：2 乘 3 是多少？
  ↓
程序把用户消息和可用工具描述交给模型
  ↓
模型提出请求：multiply，参数 a=2、b=3，调用 ID 为 call_001
  ↓
程序根据工具名找到 multiply，并执行 multiply(2, 3)
  ↓
函数返回 6；程序将结果和调用 ID 包装为工具消息
  ↓
程序再次请求模型，模型结合结果回答用户
```

调用 ID 把某条工具结果与模型提出的某次调用对应起来，一次有多个请求时尤其有用。模型也可能直接回复，而不提出工具调用。

## 4. 工具描述与工具函数

示例中的 `add` 和 `multiply` 是真正执行计算的 Python 函数。`tools` 列表则是工具描述，告诉模型工具的名称、用途、参数类型，以及哪些参数必填。它像说明书，函数体才负责计算。

应用不必总把系统里所有工具都提供给模型：可以按功能场景等方式选择一组工具。本示例将两个工具的描述绑定到模型调用配置。模型一般接收工具描述，而非需要接收整个 Python 函数源码。

## 5. 程序是如何接收模型回复的

`ChatOpenAI(...)` 创建并配置用于访问模型服务的对象；`bind_tools(...)` 为后续模型调用绑定工具描述；`invoke(messages)` 发起请求并等待响应。示例不是永久监听，而是主动请求、等待这次响应、再处理返回的 `ai_msg`。流式输出是另一种接收响应的方式。

```python
ai_msg = llm_with_tools.invoke(messages)
messages.append(ai_msg)
```

第一行获取模型回复，第二行把回复加入对话记录。`tool_choice="auto"` 允许模型自行决定是否使用工具，所以“2+1”等简单问题也可能直接得到文本回答。

## 6. 程序如何找到并执行函数

模型返回的工具名首先只是名字。程序准备一张“名字 → 实际函数”的字典：

```python
tool_dict = {"add": add, "multiply": multiply}
selected_tool = tool_dict[tool_call["name"].lower()]
tool_output = selected_tool(**tool_call["args"])
```

假设模型返回名字 `multiply` 和参数 `{"a": 2, "b": 3}`，程序先查到 `multiply` 函数，再把参数传入执行，得到 `6`。`**` 在这里将参数字典展开成关键字参数。实际应用还需要处理未知工具、无效参数及执行错误。

## 7. ToolMessage 做什么

`ToolMessage` 是工具结果的消息包装，不会自己查找工具、执行工具或请求模型。模型的调用请求记录在 `ai_msg` 中；函数执行后，程序把结果放入 `ToolMessage`：

```python
tool_message = ToolMessage(
    content=tool_output,
    tool_call_id=tool_call["id"]
)
messages.append(tool_message)
final_response = llm_with_tools.invoke(messages)
```

`content` 是工具执行结果，`tool_call_id` 用来关联对应的调用请求。`append` 只把消息放入本地列表；随后的 `invoke` 才把包含用户消息、模型调用请求和工具结果的对话交给模型，取得新的模型响应。

示例通过 `for` 依次处理第一次模型回复中可能包含的多个工具请求，每个结果都加入 `messages`；处理完毕后才再次调用模型并打印回复。第二次调用传入的对话包含用户问题、模型的工具请求和对应工具结果。它没有继续循环处理第二次回复中可能出现的新工具调用。后续的 Agent 示例会展示由框架管理更多工具循环。

如果第一次模型回复没有工具请求，程序走 `else` 分支，直接打印 `ai_msg.content`，不会执行工具或发起上述第二次调用。

## 8.总步骤
### **1. 假设模型返回**

```
调用 multiply，参数 a=2、b=3，调用 ID 是 call_001
```
### **2. 记录模型回复**

```python
messages.append(ai_msg)
```

### **3. 程序执行工具**

```python
selected_tool = tool_dict[tool_call["name"].lower()]
tool_output = selected_tool(**tool_call["args"])
```

### **4. 把工具结果包装成ToolMessage**

```python
tool_message = ToolMessage(
    content=tool_output,
    tool_call_id=tool_call["id"]
)
```
这时 tool_message 里可以理解为保存了：
```ini
工具结果：6
对应的调用 ID：call_001
```
ToolMessage 像一张结果回执：content 写工具返回了什么，tool_call_id 写这份结果对应模型提出的哪一次调用。
注意，这里记录的是工具执行结果。模型之前返回的调用请求，保存在前面的 ai_msg 中。

###   **5. 把结果加入对话记录，再次请求模型**

```ini
messages.append(tool_message)
final_response = llm_with_tools.invoke(messages)
```
### 整个过程
```ini
模型返回调用请求
       ↓
程序保存 ai_msg
       ↓
程序找到函数并执行
       ↓
ToolMessage 包装工具执行结果
       ↓
程序把 ToolMessage 加入 messages
       ↓
程序再次调用模型
       ↓
模型生成最终回复
```
## 9. ToolMessage 创建之后，程序做了什么
假设这次模型选择add工具，提出的请求是：
```ini
工具名：add
参数：a=2，b=1
调用 ID：call_001
```
程序已经执行了add(2,1)，得到结果3，并创建了ToolMessage：
```python
tool_message = ToolMessage(
    content=tool_output,
    tool_call_id=tool_call["id"]
)
```
其中 tool_output 是 3，tool_call_id 是 call_001。下面继续往下走。
### 第一步：将工具结果放入对话记录
```python
messages.append(tool_messgae)
```
messages 可以理解为程序维护的一份对话记录列表。append 的意思是：把一个新内容添加到列表末尾。
在执行这行代码之前，messages 里已经有两部分内容：

```ini
1. 用户消息：2+1 等于多少？
2. 模型消息：请求调用 add，参数 a=2、b=1，ID=call_001
```

执行 messages.append(tool_message) 后，列表变成：

```
1. 用户消息：2+1 等于多少？
2. 模型消息：请求调用 add，参数 a=2、b=1，ID=call_001
3. 工具消息：结果为 3，对应的调用 ID 是 call_001
```

### 第二步：处理完这一轮可能存在的其他工具请求

```python
for tool_call in ai_msg.tool_calls:
    # 查找并执行工具
    # 创建 tool_message
    messages.append(tool_message)
```

为什么要循环？

因为模型的一次回复中，**可能提出不止一个工具调用请求**。例如它可能一次提出两个计算请求。程序就会依次处理列表中的每个 [`tool_call`](idea://symbol/tool_call)，每完成一个，就把对应的结果加入 `messages`。

等 `for` 循环处理完后，程序才继续执行后面的代码：

```python
print(f"\n第一轮对话结束，message中增加tool_output之后：\n{messages}")
```

### 第三步：第二次调用模型

```python
final_response = llm_with_tools.invoke(message)
```

我们之前见过 `invoke(messages)`。第一次调用时，`messages` 中主要是用户问题；而**这一次的 `messages` 已经包含了模型提出的工具请求和工具执行结果**。

因此，第二次发给模型的对话可以理解为：

```ini
用户：2+1 等于多少？

模型之前提出的请求：
调用 add，参数 a=2、b=1，ID=call_001

工具返回：
结果为 3，关联 ID=call_001
```

模型收到这些信息后，可以根据工具结果生成新的回复，例如：

```ini
2+1 等于 3。
```

### **第四步：打印模型回复**

接下来：

```
print(f"\n最终模型响应：\n{final_response.content}")
```

[`final_response`](idea://symbol/final_response) 是模型返回的消息对象；这里使用 `.content` 取出其中的文本内容，然后打印到控制台。

如果模型返回的文本是“2+1 等于 3”，控制台就会显示类似：

```ini
最终模型响应：
2+1 等于 3。
```

**有两个分支值得认识。**

如果模型第一次回复时**没有提出工具调用**，程序会进入 `else`：

```
else:
    print("模型未生成工具调用的内容，直接返回文本:")
    print(ai_msg.content)
```

也就是说，模型可能直接回答“2+1 等于 3”。这时程序不会执行工具，也不会进入上面的第二次模型调用。

另外，这个示例把第二次模型调用的结果命名为 [`final_response`](idea://symbol/final_response)，但模型第二次也**可能继续提出新的工具请求**。当前代码只打印它的 `content`，没有继续检查和执行新的工具请求。这是这个基础示例的处理范围；后面学习 Agent 时，我们再看框架如何管理更多轮工具调用。

把 [`ToolMessage`](idea://symbol/ToolMessage) 之后的流程连起来：

```
创建 ToolMessage
       ↓
加入 messages
       ↓
如果还有其他工具请求，继续逐个处理
       ↓
所有工具结果都加入 messages
       ↓
再次调用模型：invoke(messages)
       ↓
取出模型回复的 content 并打印
```

## 10. 装饰器方法
为了解决工具越来越多的问题，我们使用LangChain提供的@tool装饰器
先理解 `@tool` 是什么
看第二个文件开头：
from langchain_core.tools import tool

这行从 LangChain 中导入 tool。下面把它写在函数上面：
```python
@tool
def add(a: int, b: int) -> int:
    """
    将数字a与数字b相加
    Args:
        a: 第一个数字
        b: 第二个数字
    """
    return a + b
```
你可以先把函数上面的 @tool 理解成：
> “请 LangChain 根据下面这个函数，帮我创建一个可以用于工具调用的工具对象。”
这里有三个部分需要分清：
```python
def add(a: int, b: int) -> int:
```

- add：函数名称，工具名称会从这里获得。
- a: int、b: int：参数及其类型信息，帮助构造参数描述。
- -> int：表示函数返回值的类型注解。
```python
"""
将数字a与数字b相加
...
"""
```

这是函数的文档字符串，用于描述函数的作用。在这个例子中，LangChain 会利用函数信息来构造工具描述，因此这段说明对模型理解工具用途很重要。
```python
"""
将数字a与数字b相加
...
"""
```
这仍然是实际干活的函数逻辑：接收两个数，返回它们的和。
`@tool` 不会在定义函数时自动执行加法。 它是把函数包装成工具对象，供后续绑定和调用。模型请求使用工具后，程序仍然需要执行它。

例如:
```python
@tool
def add(a: int, b: int) -> int:
    """将数字a与数字b相加"""
    return a + b
```
可以分成两部分来理解：
一部分是工具的说明信息：
```ini
工具名：add
工具用途：将数字a与数字b相加
参数：a 和 b，类型都是 int
```
这些信息主要来自函数名、参数类型注解和文档字符串。之后程序把工具绑定到模型时，框架可以利用这些信息生成模型需要的工具描述
另一部分是原来的执行逻辑：
```python
return a + b
```
这段逻辑仍然保留着。等程序需要执行工具时，可以通过包装后的工具对象来调用它，例如：
```python
add.invoke({"a": 2, "b": 1})
```
执行后得到 3。这个 .invoke(...) 是程序主动调用工具对象，不是 @tool 在定义时自动执行了函数。

还有一个小区分：函数里用三引号写的说明，叫文档字符串；像` # 这是注释` 这样的普通注释，是另一种东西。在这个例子中，我们主要关注函数名、类型注解和文档字符串。
所以可以这样记：
```ini
原来的 Python 函数
        ↓ @tool 包装
工具对象 = 工具描述信息 + 可供调用的执行能力
```
**第一个示例：列表装的是描述**
```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "add",
            "description": "将数字a与数字b相加",
            "parameters": {
                # 参数 a、b 的类型和必填要求
            }
        }
    },
    # multiply 的描述……
]
```
这里的 ``tools[0]`` 是一个 Python 字典。它描述了工具的名字、用途和参数，但这个字典本身不能计算 2 + 1。
真正做计算的是另外定义的函数：
```python
def add(a: int, b: int) -> int:
    return a + b
```
所以第一个示例里，可以看成有两样分别存放的东西：
```python
tools 列表里的字典 → 描述 add 是什么
add 函数           → 真正执行加法
```
模型提出调用后，程序再通过下面的字典找到实际函数：
```python
tool_dict = {"add": add, "multiply": multiply}
```
**第二个示例：列表里装的是工具对象**
`add` 和 `multiply` 先经过了 `@tool` 包装：
```python
@tool
def add(a: int, b: int) -> int:
    """将数字a与数字b相加"""
    return a + b
```
然后代码写：
```python
tools = [add, multiply]
```
这里的` add `和` multiply `已经是包装后的工具对象。这些对象既包含用于描述工具的信息，也保留了调用原来函数的能力。
因此，第二个示例的` tools `可以这样理解：
```
tools 列表
├── add 工具对象
│   ├── 名称、用途、参数等信息
│   └── 执行原来 add 函数的能力
│
└── multiply 工具对象
    ├── 名称、用途、参数等信息
    └── 执行原来 multiply 函数的能力
```
```python
# 工具列表绑定模型
llm_with_tools = llm.bind_tools(tools, tool_choice="auto")
```
虽然两个 tools 列表的内容不一样，LangChain 都能根据提供的工具信息，准备好模型调用所需的工具描述：
* 第一个示例：描述已经由我们手写好了。
* 第二个示例：框架从 @tool 创建的工具对象中获取描述信息。
发送给模型用于选择工具的，仍然是工具的描述信息；工具对象的执行能力留在程序这一边。模型返回调用请求后，还需要程序处理。

这是因为模型返回的仍然是一个名字，例如 "add"。程序需要通过这个名字，找到对应的工具对象
```python
tool_dict = {"add": add, "multiply": multiply}
```
这是因为模型返回的仍然是一个名字，例如 "add"。程序需要通过这个名字，找到对应的工具对象。
但两个示例找到的对象不同，执行方式也不同：
```python
# 第一个示例：selected_tool 是普通 Python 函数
tool_output = selected_tool(**tool_call["args"])
```
```python
# 第二个示例：selected_tool 是 @tool 包装后的工具对象
tool_output = selected_tool.invoke(tool_call["args"])
```
假设模型返回：
```python
tool_call["args"] = {"a": 2, "b": 1}
```
那么第二个示例相当于：
```python
add.invoke({"a": 2, "b": 1})
```
结果同样是 3。

 > selected_tool.invoke(tool_call["args"])，为什么第二个示例不需要用 ** 解包参数？

```python
# 第一个示例：调用普通 Python 函数
selected_tool(**tool_call["args"])
```
```python
# 第二个示例：调用工具对象的 invoke 方法
selected_tool.invoke(tool_call["args"])
```
**第一步：普通函数需要两个参数**
假设有一个普通函数：
```python
def add(a, b):
    return a + b
```
调用时，需要给它 a 和 b 两个参数：
```python
add(a=2, b=1)
```
但模型返回的参数放在一个字典里：
```python
args = {"a": 2, "b": 1}
```
如果直接写：
```python
add(args)
```
Python 会把整个字典当成第一个参数 a 的值，而没有收到必需的参数 b，因此会报错。 

**第二步：`**`把字典展开**

在函数调用中，`**` 可以把字典展开成关键字参数：
`add(**args)`
相当于：
`add(a=2, b=1)`
所以第一个示例写：
```python
selected_tool(**tool_call["args"])
```
是因为 selected_tool 在那里是普通 Python 函数，需要将参数字典展开后传进去。

**第三步：工具对象的 .invoke() 接收一份输入**
第二个示例中，selected_tool 是经过 @tool 包装的工具对象。它的 .invoke() 可以直接接收一个参数字典：
```python
selected_tool.invoke({"a": 2, "b": 1})
```
这里传给 .invoke() 的是一个完整的字典。工具对象再根据自己的参数定义处理这份输入，并调用原来的函数。
可以这样理解：
```
{"a": 2, "b": 1}
        ↓ 整个字典交给工具对象
selected_tool.invoke(...)
        ↓ 工具对象处理参数并调用原函数
add(a=2, b=1)
        ↓
结果：3
```
因此，不是说字典里的 a 和 b 没有被使用，而是你不需要在调用 .invoke() 时手动用 ** 展开它们。
如果在第二个示例中写成：
```python
selected_tool.invoke(**{"a": 2, "b": 1})
```
就相当于：
```python
selected_tool.invoke(a=2, b=1)
```
这会把 a 和 b 当作传给 .invoke() 方法本身的关键字参数，而不是把一个字典作为工具输入传入。它不符合这里期望的调用方式，通常会报错。
把两个示例放在一起：
```python
args = {"a": 2, "b": 1}

# 普通函数：把字典展开为 a=2, b=1
add(**args)

# 工具对象：把整个字典作为输入交给 invoke
add_tool.invoke(args)
```
这里的 `add_tool` 只是为了方便区分而起的示意名称。项目第二个文件中，经过 `@tool` 包装后，工具对象仍然叫 `add`。
## 11.padantic方法
**Pydantic是一个用于定义和验证数据结构的Python库。**
### 一. 为什么要检查参数
之前的例子里，模型可能返回：
```python
{"a": 2, "b": 1}
```


程序拿到这个字典后，准备交给加法工具。但模型返回的参数不一定总是符合预期。例如：
```python
{"a": 2}                         # 缺少 b
{"a": "不是数字", "b": 1}        # a 不是有效的整数
```


程序需要一种方式来描述规则，并检查数据是否符合规则：
```ini
a：必填，应该是整数
b：必填，应该是整数
```
### 二、先看代码如何引入 Pydantic
```python
from pydantic import BaseModel, Field
```
- BaseModel：用于创建一个数据模型。你可以先把它理解成“定义数据规则的基础”。
- Field：用于给模型里的字段补充信息，例如是否必填、字段描述等。
```python
class Add(BaseModel):
    """将两个数字相加"""

    a: int = Field(..., description="第一个数字")
    b: int = Field(..., description="第二个数字")
```
| 字段 | 类型 | 是否必填 | 描述
| --- | ---| ---| ---|
| a | int | 是 | 第一个数字
| b | int | 是 | 第二个数字

### **三.  逐段拆解 a 这一行**
```python
a: int = Field(..., description="第一个数字")
```
```ini
a
→ 字段名称叫 a

: int
→ 希望这个字段符合整数类型

Field(...)
→ 使用 Field 补充这个字段的定义

...
→ 这个字段必填，没有提供默认值

description="第一个数字"
→ 给这个字段写一段描述

```

### 四、规则定义好后，什么时候检查数据？
定义 Add 类只是写好了规则。真正拿数据来创建对象时，Pydantic 才会检查输入。例如：
```python
data = Add(a=2, b=1)
```


Pydantic 根据 Add 的定义检查 a 和 b，符合规则后创建对象。之后可以通过字段名读取值：
```python
data.a  # 2
data.b  # 1
```

如果缺少必填字段，例如：
```python
data = Add(a=2)
```


因为没有提供 b，创建对象时就会发生验证错误。
这个示例中，项目代码使用模型返回的参数创建对象：
```python
tool_obj = selected_tool_cls(**tool_call["args"])
```

你已经认识这里的 **：假设模型返回：
```python
tool_call["args"] = {"a": 2, "b": 1}
```


并且 selected_tool_cls 是 Add，那么这行就相当于：
```python
tool_obj = Add(a=2, b=1)
```

创建对象时，Pydantic 会根据 Add 的字段定义验证这两个参数。
