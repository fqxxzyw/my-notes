# Day12 前八节学习回顾：项目记忆管理

## 一、演讲回顾稿

大家好，今天我主要回顾一下昨天学习的内容：**Voyage 智途项目中的记忆管理模块**。

昨天的核心问题是：用户和智能体进行多轮对话时，系统怎样保存之前的信息，又怎样在下一次对话中把这些信息用起来。

比如，用户前面说过自己喜欢坐高铁二等座，后面再说“帮我查一下去上海的车票”，系统如果能记住他的偏好，就可以在处理当前问题时参考之前的信息。这就是记忆管理的价值。

在这个项目中，记忆管理主要由 `ConversationMemory` 类负责，代码位于 `core/memory_manager.py`。它围绕用户 ID 管理不同用户的记忆，并配合 MySQL 保存需要持久化的数据。

项目把记忆相关的数据分成了四部分。

第一部分是**短期对话记忆**，记录最近的用户提问和助手回答。代码默认保留最近 10 条消息。这里要注意，一问一答通常是两条消息，所以 10 条消息不一定等于 10 轮对话。

短期记忆主要有三个操作：添加消息、从数据库加载消息，以及把消息列表转换成文本。转换后的文本可以放进提示词，让大模型结合前面的对话理解当前问题。

第二部分是**用户偏好**，比如用户喜欢二等座、经济舱，或者偏好某种旅行方式。项目先用字典保存这些偏好，再把它们写入数据库。

数据库中使用用户 ID 和偏好名称作为联合主键。这样同一个用户可以有多种不同的偏好；当同一个偏好的值发生变化时，就更新原来的值。

第三部分是**当前任务上下文**。比如当前正在处理火车票查询，就可以在字典中记录当前任务类型、查询内容等信息。这部分数据在当前代码中保存在内存里，没有写入数据库。

第四部分是项目中称为**长期记忆**的用户提问历史。它记录意图类型、用户问题和时间，不保存助手的回答。内存中默认保留最近 20 条，重新加载时也默认读取最近 20 条。

这里需要区分内存和数据库：代码会限制内存中的记录数量，但写入 `query_history` 表时没有同步删除更早的记录。

从整个调用流程看，用户进入系统后，聊天核心会根据用户 ID 初始化记忆对象，并加载该用户已有的对话、偏好和提问历史。处理问题时，短期对话、用户偏好和当前任务上下文会用于构造意图识别提示词；处理过程中和返回回答前，系统还会更新相关记忆。

此外，昨天还学习了**序列化和反序列化**。项目中的 `to_dict()` 可以把记忆对象中的数据整理成字典，`from_dict()` 可以根据字典重新构造对象。进一步使用 JSON 等格式，就能方便地存储或者传输数据。

最后，老师还介绍了记忆压缩、分级记忆等扩展思路。不过当前项目主要实现的是消息数量限制、用户偏好和提问历史，并没有实现完整的分级压缩记忆。

我的回顾就是这些。

## 二、代码重点笔记

### 1. 记忆管理解决什么问题？

核心可以概括为四个动作：

```text
保存记忆 → 加载记忆 → 使用记忆 → 更新或清除记忆
```

例如：

```text
用户第一次提问：
“我喜欢坐高铁二等座。”

系统保存偏好：
座位偏好 = 二等座

用户后续提问：
“帮我查一下明天去上海的高铁。”

系统处理时：
把当前问题和用户偏好提供给模型参考
```

对于生成文件的场景，对话记忆通常可以保存**回答和文件路径**；文件本身是否放进记忆，需要根据业务设计，不能一概而论。

### 2. 记忆对象：一个对象绑定一个用户 ID

核心代码：[core/memory_manager.py](D:/soft/python/Voyage智途A2A/core/memory_manager.py:16)

```python
class ConversationMemory:
    def __init__(self, user_id: str, messages_limit: int = 10):
        self.user_id = user_id
        self.short_term_messages = []
        self.messages_limit = messages_limit
        self.user_profile = {}
        self.current_task = {}
        self.entity_history = []
        self._db = MySQLManager()
```

| 属性 | 作用 | 数据结构 |
|---|---|---|
| `user_id` | 标识当前用户 | 字符串 |
| `short_term_messages` | 最近的对话消息 | 列表 |
| `messages_limit` | 短期消息数量上限 | 整数，默认 10 |
| `user_profile` | 用户偏好 | 字典 |
| `current_task` | 当前任务上下文 | 字典 |
| `entity_history` | 用户提问历史 | 列表 |
| `_db` | 数据库操作对象 | `MySQLManager` 对象 |

**重点：** 数据库读写和清除时都使用 `user_id`，以区分不同用户的数据。

### 3. 短期对话记忆

短期记忆记录用户和助手最近的消息，例如：

```python
[
    {"role": "user", "content": "北京今天天气怎么样？"},
    {"role": "assistant", "content": "北京今天……"},
]
```

主要有三个方法：

| 方法 | 作用 |
|---|---|
| `add_message()` | 添加消息，并尝试写入数据库 |
| `load_messages_from_db()` | 从数据库加载消息到内存 |
| `get_short_term_text()` | 将消息列表转换成提示词可用的文本 |

#### 添加消息的流程

```text
将新消息添加到内存列表
  ↓
获取该用户当前最大的 message_order
  ↓
将新消息插入数据库
  ↓
如果数据库消息数超过上限，删除最旧的多余消息
  ↓
内存中保留最近 messages_limit 条
```

保留最近消息的代码使用切片：

```python
self.short_term_messages = self.short_term_messages[-self.messages_limit:]
```

例如列表有 15 条消息、上限为 10 条时，保留最后 10 条。

**注意：** 数据库写入失败时，代码中的异常和提前返回路径会影响后续清理，因此不能把内存和数据库始终一致当成绝对保证。

#### 转成提示词文本

`get_short_term_text()` 会把列表转换成类似下面的形式：

```text
User: 北京今天天气怎么样？
Assistant: 北京今天……
User: 那明天呢？
```

这样模型就能结合前面的对话，理解“那明天呢”里的省略信息。

### 4. 用户偏好

代码位置：[用户偏好方法](D:/soft/python/Voyage智途A2A/core/memory_manager.py:119)

用户偏好以字典形式保存：

```python
{
    "座位偏好": "二等座",
    "飞机舱位": "经济舱"
}
```

三个主要方法：

| 方法 | 作用 |
|---|---|
| `update_profile()` | 更新内存字典，并写入数据库 |
| `load_profile_from_db()` | 从数据库读取用户偏好 |
| `get_profile_text()` | 将偏好转换为文本，供提示词使用 |

#### 为什么使用联合主键？

`user_profiles` 表使用：

```text
(user_id, profile_key)
```

作为联合主键，定义见 [mysql_init.py](D:/soft/python/Voyage智途A2A/data_init/mysql_init.py:194)。

例如：

| user_id | profile_key | profile_value |
|---|---|---|
| user001 | 座位偏好 | 二等座 |
| user001 | 飞机舱位 | 经济舱 |

这样：

- 同一个用户可以有多个不同的偏好。
- 同一个用户的同一个偏好只有一条当前记录。
- 偏好改变时，可以更新原来的值。

项目使用 `INSERT ... ON DUPLICATE KEY UPDATE`：没有对应记录时插入；发生主键冲突时更新偏好值。

当前表主要保存**最新偏好值**，不等于完整保存了用户偏好的变化历史。

### 6. 长期记忆：用户提问历史

代码位置：[update_entities 和 load_entities_from_db](D:/soft/python/Voyage智途A2A/core/memory_manager.py:165)

项目中所谓的长期记忆，主要保存：

```python
{
    "type": "weather",
    "query": "北京明天天气怎么样？",
    "timestamp": "2026-11-27 10:00:00"
}
```

保存的内容包括：

- 意图类型；
- 用户问题；
- 时间。

**不保存助手回答。**

更新时：

```text
添加到 entity_history
  ↓
内存列表只保留最近 20 条
  ↓
向 query_history 表插入一条记录
```

重新加载时，默认从数据库读取最近 20 条。

#### 为什么先倒序查询再反转？

```text
数据库按时间倒序查询
  → 先选出最近的 20 条

将结果反转
  → 展示顺序变成旧的在前、新的在后
```

**这里要纠正文稿中的一个说法：** 带有 `LIMIT 20` 时，“倒序取 20 条再反转”和“直接升序取 20 条”通常不一样。前者拿到的是**最近 20 条**；后者通常拿到的是**最早 20 条**。

### 8. 序列化与反序列化

代码位置：[to_dict 和 from_dict](D:/soft/python/Voyage智途A2A/core/memory_manager.py:242)

项目中的转换过程：

```text
ConversationMemory 对象
        ↓ to_dict()
Python 字典
        ↓ json.dumps()
JSON 字符串
```

反过来：

```text
JSON 字符串
        ↓ json.loads()
Python 字典
        ↓ from_dict()
ConversationMemory 对象
```

示例：

```python
import json

# 对象 → 字典
memory_dict = memory.to_dict()

# 字典 → JSON 字符串
json_text = json.dumps(memory_dict, ensure_ascii=False)

# JSON 字符串 → 字典
restored_dict = json.loads(json_text)

# 字典 → 对象
restored_memory = ConversationMemory.from_dict(
    restored_dict,
    user_id="user001"
)
```

`to_dict()` 可以理解为先把对象数据整理成便于进一步编码的结构；`json.dumps()` 才把字典编码成 JSON 字符串。

**代码细节：** 当前 `to_dict()` 只导出最近 **5 条** `entity_history`；平时内存中保留最近 **20 条**。这两个数字对应不同操作。

序列化的目的，是让数据更方便地**存储、传输和恢复**。JSON 是常见格式，但并不是唯一方式，也不是所有对象都能自动转换成 JSON。

### 9. 记忆模块在项目中的位置

聊天核心代码位于 [core/chat_service_core.py](D:/soft/python/Voyage智途A2A/core/chat_service_core.py:294)。

```text
用户发起对话
  ↓
聊天核心根据用户 ID 创建记忆对象
  ↓
加载用户偏好、提问历史、短期消息
  ↓
记录当前用户消息
  ↓
构造提示词：短期对话 + 用户偏好 + 任务上下文 + 当前问题
  ↓
意图识别、路由和任务执行
  ↓
记录助手回答
  ↓
返回结果
```

记忆管理为主 Agent 服务，帮助它理解上下文；缓存则用于复用结果，两者作用不同。

**结合当前代码的准确说法：** 初始化时会加载提问历史，但在目前看到的意图识别提示词参数中，直接传入的是短期对话、用户偏好和当前任务上下文；不能简单说已经把加载的长期提问历史全部注入了提示词。

### 10. 课程提到的扩展思路

老师还讲了更复杂的记忆策略：

- **记忆压缩**：把较早的多轮对话总结成较短文本。
- **分级记忆**：近期内容保留得更详细，较早内容保留摘要。
- **用户明确要求长期记住的内容**：可以设计成单独的长期规则，再决定何时读取。
- **图记忆**：通过实体和关系组织信息，按需检索相关内容。

这些是可以进一步设计的方向。**当前项目代码没有实现完整的分级压缩记忆或图记忆。** 图记忆与分级记忆也不是同一个概念：前者侧重关系组织和检索，后者侧重不同层次的保存与管理；两者可以结合使用。
