# 第一部分：记忆管理模块

## 二、为什么需要记忆管理？

大模型处理问题时，需要知道用户当前说的话，也需要适当了解之前的对话。

例如：

```text
用户：我明天要去成都。
助手：好的。

用户：那边天气怎么样？
```

如果没有之前的对话，系统可能不知道“那边”指哪里。结合历史消息后，系统才能理解用户想查询**成都明天的天气**。

记忆管理主要解决四个问题：

- **存什么**：对话消息、用户偏好、历史提问等。
- **怎么存**：保存在内存中，或持久化到数据库。
- **怎么用**：加载后放入提示词，供大模型参考。
- **怎么清理**：超过数量限制时删除旧内容，或者按用户清空。

## 三、项目中的四类记忆数据

| 类型 | 保存内容 | 存储方式 |
|---|---|---|
| 短期对话 | 最近的用户提问和助手回复 | 内存列表 + MySQL |
| 用户偏好 | 座位、舱位等偏好 | 内存字典 + MySQL |
| 当前任务上下文 | 当前意图、查询等任务信息 | 内存字典 |
| 用户提问历史 | 意图、问题和时间 | 内存列表 + MySQL |

每个 `ConversationMemory` 对象都绑定一个 `user_id`，通过用户 ID 区分不同用户的数据。

### 1. 短期对话记忆

短期记忆记录最近的消息，主要包括：

```python
{
    "role": "user",
    "content": "北京明天天气怎么样？",
    "timestamp": "10:30:00"
}
```

主要操作：

- `add_message()`：添加消息并写入数据库。
- `load_messages_from_db()`：从数据库恢复消息。
- `get_short_term_text()`：将消息列表转换成文本，放进提示词。

默认保留最近 **10 条消息**。一问一答通常是两条消息，所以不一定是 10 轮对话。

超过上限时，代码会按消息顺序删除较早的记录；内存列表也通过切片保留最近的消息。

### 2. 用户偏好

用户偏好以字典形式保存，例如：

```python
{
    "座位偏好": "二等座",
    "飞机舱位": "经济舱"
}
```

主要操作：

- `update_profile()`：更新偏好并写入数据库。
- `load_profile_from_db()`：从数据库读取偏好。
- `get_profile_text()`：将偏好转换成文本。

数据库使用 `user_id` 和 `profile_key` 作为联合主键。这样，一个用户可以有多个偏好；同一个偏好的值变化时，可以更新原值。

### 3. 当前任务上下文

当前任务上下文记录正在处理的任务信息，例如：

```python
{
    "type": "train",
    "query": "查询北京到上海的高铁"
}
```

代码通过 `update_task_context()` 更新字典。当前实现把它保存在内存中，没有单独写入数据库。

### 4. 用户提问历史

项目中称为长期记忆的部分，主要记录：

```python
{
    "type": "weather",
    "query": "北京明天天气怎么样？",
    "timestamp": "提问时间"
}
```

它保存的是**用户问题、意图和时间**，不包含助手回答。

内存中默认保留最近 20 条；从数据库恢复时也默认读取最近 20 条。数据库插入逻辑没有同步删除更早的提问记录。

## 四、清除记忆与序列化

### 清除记忆

`clear_memory()` 会清空当前对象中的记忆数据，并根据 `user_id` 删除数据库中对应用户的短期消息、偏好和提问历史。

### 序列化与反序列化

项目提供了两个方法：

```text
记忆对象
  ↓ to_dict()
Python 字典
```

```text
Python 字典
  ↓ from_dict()
记忆对象
```

如果还需要传输或以 JSON 格式保存，可以继续转换：

```text
对象 → 字典 → JSON 字符串
JSON 字符串 → 字典 → 对象
```

序列化的作用是让数据更方便地存储、传输和恢复。

## 五、记忆管理在整个项目中的位置

记忆模块为主 Agent 服务：

```text
用户开始对话
  ↓
根据 user_id 创建记忆对象
  ↓
加载短期消息、用户偏好和提问历史
  ↓
主 Agent 处理当前问题
  ↓
处理过程中更新任务信息和提问历史
  ↓
记录助手回答
```

其中，短期对话、用户偏好和当前任务上下文会被用于构造意图识别提示词。

可以这样理解：

> 记忆模块负责管理上下文，主 Agent 负责利用上下文处理问题。

# 第二部分：主 Agent 核心层

## 六、主 Agent 的作用

主 Agent 相当于整个旅行助手的**总调度员**。

它不一定亲自完成所有业务，而是负责：

1. 理解用户想做什么。
2. 判断应该交给哪个 Agent。
3. 对复杂任务进行拆分和规划。
4. 获取执行结果并组织回复。

核心代码：[core/chat_service_core.py](D:/soft/python/Voyage智途A2A/core/chat_service_core.py:62)

---

## 七、主 Agent 的提示词

代码位置：[core/prompts.py](D:/soft/python/Voyage智途A2A/core/prompts.py:24)

项目针对不同任务设计了不同的提示词：

| 提示词 | 作用 |
|---|---|
| 意图识别提示词 | 判断用户意图，改写问题，必要时追问 |
| 景点推荐提示词 | 根据用户需求生成景点推荐 |
| 规划与反思提示词 | 将复杂任务拆成步骤，判断是否需要继续执行 |
| 结果汇总提示词 | 将多个步骤的结果整理成最终回复 |

提示词要告诉大模型：**做什么、参考什么、按照什么格式输出**。

例如，意图识别要求输出意图列表、改写后的问题，以及必要时的追问内容。

## 八、主 Agent 初始化：注册子 Agent

主 Agent 启动时会读取配置，将子 Agent 的信息保存到注册表中。

```text
读取 config.yaml
  ↓
获取子 Agent 的名称和服务地址
  ↓
创建 A2A 客户端
  ↓
保存到 _agent_registry 注册表
```

注册表相当于一张通讯录，记录：

```text
子 Agent 名称
子 Agent 地址
A2A 客户端
Agent 名片
```

后续需要调用某个子 Agent 时，主 Agent 就可以通过注册表找到它。

## 九、意图与 Agent 的映射

主 Agent 会读取子 Agent 名片中的技能信息，建立：

```text
意图标识 → 对应的 Agent
```

例如：

```text
天气查询意图 → 天气 Agent
票务查询意图 → 票务 Agent
景点推荐意图 → 主 Agent 内部处理
```

这样，用户意图识别完成后，系统就能根据映射找到对应的处理者。

其中，项目把 `attraction` 景点推荐映射为 `__local__`，表示由主 Agent 进程内的逻辑处理。

## 十、加载 Agent 技能和用户记忆

初始化时，主 Agent 还会：

- 获取各子 Agent 的名称、技能和描述；
- 将这些信息整理成文本；
- 加载当前用户的短期对话、用户偏好和提问历史。

这些信息让主 Agent 知道：

```text
系统有哪些能力？
用户之前说过什么？
当前问题应该交给谁？
```

## 十一、景点推荐 Agent

景点推荐由主 Agent 内部的 `_local_agent()` 处理。

```text
用户请求景点推荐
  ↓
识别出 attraction 意图
  ↓
调用景点推荐提示词
  ↓
调用大模型生成推荐
  ↓
返回结果
```

这里的“内部处理”是说这段处理逻辑在主 Agent 进程中，仍然需要调用项目配置的大模型。

---

## 十二、意图识别 Agent

意图识别的目的是回答：

> 用户这次到底想做什么？

它会结合：

- 用户当前输入；
- 短期对话历史；
- 用户偏好；
- 当前任务上下文；
- 系统支持的 Agent 和技能。

### 例子：结合历史改写问题

```text
用户：我明天要去成都。
用户：那边天气怎么样？
```

意图识别可以结合前文，将问题改写为：

```text
查询成都明天的天气。
```

如果信息仍然不足，系统可以追问；如果问题超出系统能力，则标记为超出范围。

---

## 十三、规划与反思 Agent

当用户一次提出多个需求时，主 Agent 可以先规划步骤。

例如：

```text
用户：查一下成都明天的天气，再推荐适合的景点。
```

系统可以拆分为：

```text
步骤 1：查询成都明天的天气
步骤 2：推荐景点
步骤 3：组织结果并回复
```

规划结果中，每个步骤会包含：

- `step`：步骤编号。
- `action`：要执行的动作。
- `intent`：对应的意图。
- `depends_on`：依赖的前置步骤。

执行一部分后，系统还可以根据已有结果进行**反思**：

```text
信息已经足够 → 结束并汇总

信息仍不完整 → 继续规划或执行后续步骤
```

---

## 十四、单一意图的执行

识别出单个意图后，主 Agent 按照映射找到对应处理者：

```text
意图 + 改写后的问题
  ↓
更新提问历史和任务上下文
  ↓
查找对应的 Agent
  ↓
本地处理或远程调用
  ↓
取得结果并组织回复
```

如果是景点推荐，就走主 Agent 内部的景点推荐逻辑。

如果是远程子 Agent，就通过 A2A 客户端发送消息，取得结果后再进行整理。

# 三、中午演讲稿

大家好，下面我回顾一下昨天学习的 Voyage 智途项目。

昨天主要学习了两部分内容：**记忆管理模块**和**主 Agent 核心层**。

首先是记忆管理。它解决的是多轮对话中的上下文问题，也就是用户之前说过什么、有什么偏好，系统怎样保存下来，并在后续对话中使用。

项目通过 `ConversationMemory` 管理用户记忆，每个对象绑定一个用户 ID，区分不同用户的数据。

记忆主要分为四类。第一类是短期对话，保存最近的用户消息和助手回答，默认保留十条消息；第二类是用户偏好，比如座位和飞机舱位偏好；第三类是当前任务上下文，记录正在处理的任务信息；第四类是用户提问历史，记录意图、问题和时间。

其中，短期对话、用户偏好和提问历史会配合 MySQL 保存，方便后续恢复。项目还提供了清除记忆的方法，以及把记忆对象转换为字典、再根据字典恢复对象的方法。

第二部分是主 Agent 核心层。主 Agent 可以理解为整个项目的总调度员，负责理解用户问题、选择处理者、规划任务和组织结果。

主 Agent 初始化时，会读取配置，注册天气、票务等子 Agent，并获取它们的技能和描述，建立意图与 Agent 之间的映射。同时，它会加载当前用户的记忆，为后续对话做准备。

当用户发来问题后，主 Agent 会结合当前输入、对话历史和用户偏好进行意图识别。比如用户先说要去成都，之后再问“那边天气怎么样”，系统就可以结合历史，把问题改写成查询成都天气。

识别出意图后，主 Agent 会找到对应的处理方式。景点推荐可以由主 Agent 内部的逻辑调用大模型完成；其他业务可以通过 A2A 协议交给对应的远程子 Agent。

如果用户一次提出多个需求，主 Agent 还可以先把任务拆成多个步骤，判断步骤之间的依赖，再根据执行结果进行反思。最后，系统整理结果、记录回答并返回给用户。

总体来说，昨天的主线就是：**记忆模块负责管理上下文，主 Agent 负责识别意图、分配任务、执行规划和汇总结果。**
